## 3. What is established (do not re-derive; verify only what you change)

- Every Compact captures at about 32 Hz and publishes one picture per four captures (steps: seed op 5, accumulate op 6 twice, mean-of-four op 7 with the publish bit) = 8 fps. The Compact PRO captures at 17.68 Hz and publishes every second
  capture = 9 fps. A patch edits the **steady self-loop block of the stream the vendor app actually uses** so it has one step: a plain copy of the capture with the publish bit, header id and gpio as stock. No accumulating op (ops that read the destination froze or
  alternated the picture). The acceptance-sum word at image `+0x238` is retuned so the 32-bit word sum over `header.length` stays the same. The picture is the stock picture without the averaging (noisier by design).
- "Mode" = the `SET_IMAGE_PROCESSING_MODE` value; in the 2014-chain firmware it indexes `frame_mode_table_r32k`, one capture program per mode. Mode 0 raw (4-step average), mode 3 Hi FPS (already one step, about 32 fps stock), mode 6
  shutter-managed correlated double sample (op 9), **mode 8 Normal**. The vendor app and the macOS app use 8 (and 3, 0). The removed 16 Hz patch edited mode 6 and so did nothing in Normal mode: **a patch is only valid if it edits the block of the mode that is measured.**
- Proven designs (copy their shape):
  - **1.3.0.0** (`compact_32k-1.3.0.0-to32`): mode-8 program, block 8 at image `+0xB898` (34-byte blocks, 2-byte steps `sel|active<<3|op<<4, push|hdr<<1|gpio<<5`): `84 08 59 20 69 20 69 20 79 27` -> `81 08 39 27 00 x6`. Measured on the owner's unit (serial 1013CE098ACA): Normal mode median 32.2 fps, 0 frozen pairs
    (measured image `d91284c6...` also carried the removed mode-6 edit; the current mode-8-only image `ef90c94a...` was **not** run on a camera yet).
  - **4.8.2.1 / Compact XR** (`compact_32k-4.8.2.1-to32`): 68-byte command page 13 at `+0x90F2`: count `04 -> 01`, substeps -> `23 81 03 01` + zeros (copy, LAST, param 0x23). Measured on the XR (serial 1E2A50YZ7628): 25 to 26 fps all frames, median 32.2, 31 ms steady, 0 frozen pairs; the page's own write was driven in Electron.
- Layouts seen: 34-byte blocks with 2-byte steps (1.2.0.0, 1.3.0.0), 52-byte blocks with 3-byte steps `{src_sel, op, hdr}` (1.3.0.8, 4.8.1.7, 4.8.1.9; the FF builds), 68-byte command pages with 4-byte substeps (4.8.2.1), Compact PRO rows (1.0.3.0 row 14, 1.0.3.2 and 4.9.x record 20/row 20).
  For 1.3.0.8 / 4.8.1.7 / 4.8.1.9 the existing 32 Hz entry edits "block 13" of a 52-byte program, and **which mode that block belongs to is not established** (the bench measured them only through the emulator stream and IP modes 6 and 9). Find out; if it is not the Normal (mode 8) steady block, add the mode-8 edit.
- Current table (`FW-V1/emu/fps_patch.py` PATCHES, ported by hand to `packages/core/src/preservation/fps-patch-table.ts`, differential fixture `packages/core/test/preservation/fps-patch-python.json`, gates `FPS_STAGE_ONE_IDS` / `FPS_STAGE_TWO_IDS`, `FPS_MEASURED_HZ`):
